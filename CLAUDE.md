## Read rules for `data/`

- Treat `data/` as read-only. Do not write, rename or reformat files there.
- Files are large. Read only the first lines with `head` when you inspect a file.
- Skip the unit row in Anttila and Särkisuo files. DuckDB applies `skip` before it reads the header. Read the names first, then read the data: `read_csv(path, header=true, all_varchar=true) LIMIT 0` gives the names, then `read_csv(path, skip=2, header=false, names=[...], nullstr='-9999')` gives the data.
- Set the missing-value string per file: `nullstr='-9999'` (Anttila, Särkisuo, Maktau), `nullstr='NA'` (Haltiala), `nullstr=''` (Qvidja, Viikki).
- Viikki EC files: `read_csv(path, delim=';', decimal_separator=',', encoding='latin-1', timestampformat='%-d.%-m.%Y %-H:%M')` or parse `Datetime` with `strptime(Datetime, '%d.%m.%Y %H:%M')`. Without `encoding='latin-1'` the read fails on line 1.
- `YYYYMMDDHHMM` timestamps (Qvidja, Maktau): read as VARCHAR or BIGINT, then `strptime(CAST(col AS VARCHAR), '%Y%m%d%H%M')`.
- Example: `SELECT * FROM read_csv('data/Haltiala/haltiala.csv', nullstr='NA') LIMIT 5;`

## Website (`site/`)

- Static Astro site (Astro 7.4.1). Apache ECharts draws the charts. DuckDB-WASM reads the Parquet files in the browser. Vanilla TypeScript and vanilla CSS only. Do not add a UI framework.
- Hosting: Cloudflare Workers static assets. `wrangler.jsonc` (root) serves `site/dist/`. No Worker script and no Astro adapter. `site/public/_headers` sets the cache rules: `/_astro/*` and `/duckdb/*` immutable for 1 year, `/data/*` 1 hour, `/version.json` `no-store`. `/duckdb/*.gz` has `Content-Type: application/octet-stream` (no `Content-Encoding`).
- The page makes no requests to other origins. All DuckDB files come from our own build. `npm run site:sync` runs `scripts/sync-site-duckdb.ts`. It writes `site/public/duckdb/` (not in git):
  - `<npm version>/duckdb-browser-{eh,mvp}.worker.js`: copies from `node_modules/@duckdb/duckdb-wasm/dist/`. The page starts the worker with `new Worker(url)`.
  - `<npm version>/duckdb-{eh,mvp}.wasm.gz`: Cloudflare accepts files up to 25 MiB only. The WASM files are 34 to 40 MB, thus the script compresses them with gzip (level 9, about 7.7 and 8.7 MB). `db.ts` fetches the file, decompresses it with `DecompressionStream('gzip')` (only if the first bytes are `1f 8b`, because a host can decode it before) and gives a blob URL (`application/wasm`) to `db.instantiate()`. `selectBundle()` picks EH or MVP.
  - `extensions/<DuckDB version>/wasm_{eh,mvp}/parquet.duckdb_extension.wasm`: the official signed parquet extension (about 3 MB). It is not on npm. The script downloads it one time from `extensions.duckdb.org` into `node_modules/.cache/inar-duckdb-ext/`. Without internet and without cache, the script fails. The DuckDB version (for example `v1.4.3`) comes from the Node build of the npm package (`getVersion()`). `db.ts` sets `custom_extension_repository` to `<origin><base>duckdb/extensions` and runs `LOAD parquet` before the first Parquet read. Our queries load no other extension. If a new query needs one (for example `json`), add it to `EXTENSIONS` in the script.
  - The script does no work for a file when the output is newer than the input. When you update `@duckdb/duckdb-wasm`, the paths change and the script removes the old versions.
- `scripts/check-dist.ts` runs in `site:build` and fails if a file in `site/dist/` is 25 MiB or larger. Do not put uncompressed `.wasm` files of DuckDB in `site/public/`.
- Data flow: `npm run build:db` writes `db/*.parquet`, `npm run calc` writes `data/calculated/`. `npm run site:sync` (`scripts/sync-site-data.ts`) copies the DB files (with `events.parquet`) to `site/public/data/` (not in git), writes `site/public/data/fluxes.parquet` (slim copy of `fluxes_30min.parquet`: `gpp`, `reco`, flags, `nee_f_calc` = the calculated gap-filled NEE for all Maktau rows and the MDS rows of the other sites, FLOAT, about 5 MB) copies the small result tables to `site/src/data/calculated/` (not in git, read at build time by the Calculated page), runs `scripts/axis-ranges.ts` (it writes `site/src/data/axis-ranges.json`, not in git, the fixed y ranges, see "Fixed y range" below) and, last, writes `site/src/data/events.json` (not in git, events with site names, read at build time by the Events page). The sync fails without `npm run calc`. The page fetches the files, registers them in DuckDB-WASM and runs SQL.
- At start, `db.ts` makes table `obs`: all columns of `observations.parquet`, `gpp` and `reco` from `fluxes.parquet` (Maktau `nee_f` = `coalesce` with the calculated value), plus `tl`, the period start in site local time (`ts_start` + `sites.utc_offset_min`). Units of `gpp`/`reco` are added in `loadMeta()`. The database stays open. `query(sql)` runs SQL on it.
- Load progress: `#loader` (`role="progressbar"`) replaces a "Loading" text. `db.ts` counts the received bytes of the WASM file and the Parquet files (`readBody()`, `setLoadProgress()`); the downloads give 0 to 90 %, the table build the rest. When a file has no `Content-Length` (for example `astro preview` sends gzip), the bar moves back and forth. `app.ts` removes the bar when `loadMeta()` is done. A diagram card with `data-status="loading"` shows a thin moving bar at the top. With `prefers-reduced-motion`, the bars pulse.
- Busy state after a parameter change: when the form debounce (300 ms) ends, `app.ts` calls `setBusy(true)` until no diagram card is `loading` (`DiagramList.whenSettled()`; ready, note or error). Busy = the top fieldsets of the form are `disabled`, the form, `#tabs` and `#chart` have `aria-busy="true"`, the tab buttons and "Add diagram" are disabled, `.params-status` (`role="status"`) says "Updating diagrams…", the cursor is `progress`. No animation. At the end the focus goes back to the changed control (`ParamsForm.setBusy()`). Tests: Playwright actions wait for enabled controls; after a change, wait for `#chart` `data-status="ready"`.
- Update check (all pages, `site/src/scripts/update.ts`, started by a script in `Base.astro`): `site/astro.config.mjs` makes one build ID (`time` in seconds, short git `commit`), gives it to the code as `__BUILD_TIME__` and `__BUILD_COMMIT__` (`vite.define`, types in `site/src/env.d.ts`) and writes `dist/version.json` (hook `astro:build:done`; `astro dev` has no file, the check gets 404 and stays silent). The page reads `version.json?t=<now>` (`cache: 'no-store'`) 5 s after the load, then every 5 minutes (`CHECK_MS`, battery) when the page is visible, and at once on `visibilitychange` (visible), `pageshow` (from the back-forward cache), `online` and after sleep (a timer tick more than 2 × `CHECK_MS` late); no check less than 30 s after the last one. All errors are silent. When `time` is not `__BUILD_TIME__`, or on `vite:preloadError` (an old `/_astro/` chunk is missing), `.update-notice` (`role="status"`, fixed at the bottom, no focus change) says that a new version is available, with Reload and Later (hides it until the next page load). `db.ts` adds `?v=<__BUILD_TIME__>` to the `/data/` URLs, so a new build never reads old cached Parquet files.
- Error recovery (`site/src/scripts/recover.ts`): when the data page cannot start (`loadMeta()` catch in `app.ts`, `start().catch` in `index.astro`), `showRecovery()` writes the error in `#status` and puts the box `#recovery` below it: button "Clear site data and reload" (`clearSiteData()`: removes the `localStorage` and `sessionStorage` keys with the prefix `inar-agri.`, the Cache Storage and the service workers, each step in try/catch; then `location.reload()`) and the hard reload shortcut in `<kbd>` (`reloadShortcut(platform, userAgent, maxTouchPoints)`: macOS Safari ⌥ Option + ⌘ Cmd + R, other macOS browsers ⌘ Cmd + ⇧ Shift + R, Windows, Linux and ChromeOS Ctrl + Shift + R or Ctrl + F5, iOS, iPadOS and Android: close the tab and open the page again; unit test `recover.test.ts`). Site data is deleted only on the button click. A diagram card error adds only the hard reload line (`hardReloadLine('span')`).
- Variables (`state.ts` `VARIABLES`, 24): Fluxes `nee, nee_f, gpp, reco, gpp_src, reco_src, ch4, n2o, le`; Meteorology `ta, sw_in, ppfd, rh, vpd, ustar, precip, pa, ws, wd, netrad, sw_out`; Soil `tsoil, swc, g`. `VARIABLE_GROUPS` makes the three checkbox groups (with All / None buttons), `VARIABLE_SITES` the site hints, `DEFAULT_VARIABLES` the five of the default view. Each variable checkbox has an ⓘ button (`.var-info-btn`). It shows the summary and the source below the checkbox, with a link to the Variables page. Steps (`AGGREGATIONS`): `raw`, `day`, `week` (local ISO week, Monday 00:00), `month`.
- Aggregation per variable (`diagrams/sql.ts`): a step (`day`, `week`, `month`) uses `stepExpr(v)`: `sum()` for `SUM_VARS` (`precip`, mm per step; a step with gaps gives a sum that is too low), the circular mean for `CIRCULAR_VARS` (`wd`, `meanExpr()`: `atan2` of the mean sine and cosine, 0 to 360°), else `avg()`. The step is the same in `timeseries`, `years`, `yearPanels`, `scatter`, `response` and the data export. ## Deep Dive

A Deep Dive is a short article that an AI assistant writes from our data. Each dive answers one question that the data can answer. The list page `/deep-dive/` shows all dives, newest first (number, title, question, short answer, sites, date, status), and a note that "Checked" means a check by two other AI models, not by a person (`CHECKED_NOTE` in `site/src/lib/deepDive.ts`; the article facts box shows the same note).

### Work with subagents

- Use subagents to keep the context window of the main agent small. Give them the tasks that read much text: read PDFs and long files, explore the data, run builds and tests, and draft long parts. The main agent keeps the decisions and the final text.
- Give each subagent a clear and short brief: the goal, the files to read, the limits, and the output that you want back (a short summary, not file dumps).
- Use the model that fits the task. The models are Fable, Opus, Sonnet and Haiku. Examples: Fable for difficult method decisions and as a further independent reviewer; Opus for the question, the method, the script and the article; Sonnet for an independent recompute and for code or test runs; Haiku for searches, simple checks and the language review. The verification steps below must use different models.
- Run independent subagents in parallel. Do not do the same work again in the main agent.

### Files

- Article: `site/src/pages/deep-dive/<slug>.mdx` (MDX, `@astrojs/mdx` 8.1.0, frontmatter `layout: ../../layouts/DeepDive.astro`). The list page `site/src/pages/deep-dive/index.astro` finds all MDX files of the folder with `import.meta.glob('./*.mdx', { eager: true })`.
- Script: `scripts/deep-dives/<slug>.ts` (Node, `@duckdb/node-api`, helpers from `scripts/lib/duck.ts` and `scripts/lib/deep-dive/`). It exports `slug`, `title`, `inputs` and `run(conn)`. It reads only `db/*.parquet` and `data/calculated/*`. Pure helpers go in `scripts/lib/deep-dive/` with a `*.test.ts` file (`npm run test:unit` runs them).
- Result: `site/src/deep-dives/<slug>.json`. `npm run deep-dives` (`scripts/deep-dives.ts`) writes it: the results, the figure data and `dataVersion` (time of the run, git commit and dirty flag, `builtAt` of `db/report.json` and `data/calculated/report.json`, size and SHA-256 of each input). Numbers have 10 significant digits. Commit the JSON: the article is a fixed snapshot.
- Shared code: `site/src/lib/deepDive.ts` (frontmatter schema, `diveNumber()`, `fmtNum()`, references, `dataPageHref()`, `checkBody()`), `site/src/lib/deepDiveChart.ts` (`renderSvg()`, colours), `site/src/lib/deepDives/<slug>.ts` (figures and tables of one dive), components in `site/src/components/deep-dive/` (`Num`, `Figure`, `Cite`, `References`), styles `site/src/styles/deep-dive.css`.

### Rules

- Language: ASD-STE100 Simplified Technical English, as in the rest of the project. Careful claims: write "associated with", not "causes". Give n and the uncertainty (SD, interval) with each result.
- No typed numbers. Each number in the text comes from the JSON through `<Num k="path.in.json" digits={n} unit="…" />` (options `sign`, `abs`, `percent`). A missing key or a value that is not a number stops the build. Tables and alt texts get their numbers from the JSON in code. The frontmatter `question` and `shortAnswer` must not contain digits.
- References: cite with `<Cite ids={[...]} note="p. 5" />` and list them with `<References ids={frontmatter.references} />`. Prefer the articles and documents in `data/` (the list shows the file path). Articles of `REFERENCES` in `site/src/scripts/glossary.ts` use their id; other sources (Hu et al. 2024 = `hu2024`, the management files, `docs/calculated.md`, `docs/anomaly-data-report.md`) are in `EXTRA_REFERENCES` of `site/src/lib/deepDive.ts`. Read the PDFs (Read tool with `pages`) to cite a claim correctly. The layout stops the build when a citation link has no entry in the list.
- Figures: build-time SVG with ECharts SSR (`renderSvg()`, as `site/src/lib/budgetFigure.ts`); no client script. Use `<Figure id title svg alt view>` with the caption as the slot: it gives `role="img"`, the `aria-label` (alt text, also shown below the caption) and the link "Open in the data page" (a `#view=` hash from `viewToHash()` for the same sites, variables and period). Use the site colours and the Okabe-Ito palette (`SERIES`, `siteColor()`, `siteSymbol()`); add a dash, a symbol or a fill pattern so that colour is not the only cue. Use the sentinel `INK` (`#7a7974`) for marks in the text colour; `deep-dive.css` maps it and all text to the page tokens (light and dark).
- Frontmatter (Valibot, `FrontmatterSchema`; a bad frontmatter stops the build): `index` (order of creation, 0 = first dive; the list page stops the build when the numbers are not 0 to n − 1 without gaps, `checkIndexes()`; the page shows "Deep Dive #<index>", `diveLabel()`), `title`, `question`, `shortAnswer` (one line), `sites` (site codes), `variables`, `period` (`{ from, to }` years), `date` (ISO, quoted), `status` (`draft` | `checked`), `models` (list of `{ model, role }`: which LLM did what), `script` (`scripts/deep-dives/<slug>.ts`), `references` (ids), `checks` (list of `{ kind: recompute | review, by, date, result: pass | fail | partial, note }`).
- Fixed structure: the layout writes the h1, the AI notice, a facts box and "Question". The MDX body has these h2 headings, in this order: "Short answer", "Data and method", "Results", "Limits and uncertainty", "References", "Reproduce". `checkBody()` stops the build on another order. "Limits and uncertainty" gives n and the spread, and links the open findings of `/data-report/` that apply (for example the 2-hour UTC offset of Anttila, Särkisuo and Viikki: say if a daily or weekly scale makes it unimportant). "Reproduce" gives the commands and the script path.
- Before a commit: `npm run deep-dives -- --check` must pass. It runs all dive scripts again and compares the results with the committed JSON (relative tolerance 1e-6, `dataVersion` is not compared). When the inputs change (`npm run build:db`, `npm run calc`), run `npm run deep-dives`, read the article again and correct the text if a statement is no longer true.

### Verification with different models

A dive is `draft` until two independent checks pass. Record each check in `checks` of the frontmatter. `status: checked` needs a passed `recompute` and a passed `review` (the schema checks this).

1. Opus writes: the question, the script, the article and the figures. Status `draft`, `checks: []`.
2. Sonnet recomputes: a new agent with the question and the method text of the article, but without the dive script and without the JSON. It writes its own SQL on `db/*.parquet` and `data/calculated/*` and compares its main numbers with the article. Result `pass` when the numbers agree (or the differences are explained).
3. Haiku reviews: the language (STE, careful claims, n and uncertainty given) and each citation against the article in `data/` (page, claim).
4. When both pass, set `status: checked`, run `npm run site:build` and commit.

### Add a new dive

1. Choose a question that the data can answer. Choose a slug (`a-z`, `0-9`, `-`). The `index` is the highest index + 1.
2. Write `scripts/deep-dives/<slug>.ts` (export `slug`, `title`, `inputs`, `run`). Put pure helpers in `scripts/lib/deep-dive/` and add unit tests.
3. Run `npm run deep-dives -- <slug>`. Check the JSON.
4. Write the figures in `site/src/lib/deepDives/<slug>.ts` (check the JSON parts with Valibot).
5. Write `site/src/pages/deep-dive/<slug>.mdx` with the frontmatter and the fixed structure. Use `<Num>` for each number.
6. Run `npm run deep-dives -- --check`, `npm run typecheck`, `npm run test:unit`, `npm run site:build` and the Deep Dive tests of `tests/site.spec.ts` (`npx playwright test -g "deep dive"`).
7. Ask for the independent checks (see above).
